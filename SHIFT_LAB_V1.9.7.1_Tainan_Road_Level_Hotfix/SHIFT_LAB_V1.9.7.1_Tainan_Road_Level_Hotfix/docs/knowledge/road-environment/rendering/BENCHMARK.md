# 畫質與網頁效能量測

「最好3D效能」定義為：在指定裝置、瀏覽器與畫面解析度下，先滿足所見即所得，再選擇能穩定達到目標幀時間的最高畫質組合。本輪只有量測設計，所有實測結果仍為null。

## 環境與測量條件

記錄CPU、GPU或可取得的adapter資訊、記憶體、作業系統、瀏覽器版本、實際後端、電源模式、視窗與內部渲染解析度、DPR、垂直同步、畫質組態、種子及程式版本。至少比較桌機獨顯與筆電內顯；行動裝置另訂規格，不把桌機成績外推。

使用原生GPU及相同攝影機路徑、速度、光照和物理負載。分開測試首次載入與暖快取，先暖機再採樣，每組重複執行；規劃暖機10秒、採樣60秒、重複3次與長時600秒，均為專案測試計畫而非既有成績。參考目標暫設60fps，即每幀約16.67ms，這是畫質比較的參考目標，不是最高FPS上限；最終裝置、顯示更新率與驗收閾值需在基線量測時明確固定。

前期headless／SwiftShader適合功能自動化，不作原生GPU性能證據。只看平均FPS會漏掉載入尖峰；不能用靜止畫面的極高FPS代表行駛。

## 必記指標

| 指標 | 測量與解讀 |
| --- | --- |
| frame interval | p50／p95／p99、超預算比例、長幀及移動中可見卡頓 |
| CPU | 物理、生成、提交渲染、資產處理與主執行緒長任務；維持原物理頻率，記錄模擬時間與牆鐘時間及丟棄步數，防止以模擬變慢取得流暢畫面 |
| GPU | 有支援時用[GPU timer](sources/GPU-TIMER.md)延後讀取，排除disjoint；無支援記錄unavailable |
| render calls／triangles | 所有陰影及後處理pass的總量，避免只統計最後一次render |
| 記憶體 | 幾何、貼圖、render target估算位元組及資源數；JS heap與GPU不可混稱 |
| 串流 | 冷載入、生成、轉碼、上傳、材質首次出現、碰撞就緒的延遲分布 |
| 畫質 | 輪廓、接縫、貼圖尺度、路面斜視清晰度、陰影、殘影及近景接地 |

[renderer.info](sources/THREE-RENDERER.md)的textures／geometries是數量，不是精確VRAM；WebGL也不能可攜地查出裝置總顯存。依[WebGL原則](sources/WEBGL-PRACTICES.md)用實際格式和render target估算預算，檢查配置與回收。CPU提交與GPU執行可能重疊，不把兩個毫秒數直接相加當整幀時間。

## 場景與畫質對照

10種場景見[benchmark-plan.json](benchmark-plan.json)，包含10材質樣板、曲坡路肩、挖填邊坡、遠山、上下橋、隧道、植被過繪、高速反向串流、切圖與長時行駛。樣板對照相同尺度、光照、車輪及鏡頭，同時拍靜態與移動畫面；材質壓縮可與未壓縮參考比對，但畫面差異不能直接等同感知品質。

先逐項改變幾何LOD、材質層數、貼圖格式、陰影、後處理與解析度，找出CPU／GPU／頻寬或記憶體瓶頸，再比較組合。WebGL2與WebGPU要確認功能及可見畫質等價，不能用少畫陰影或省掉地形的版本取得比較優勢。

## 品質調節順序

保持接觸區幾何、障礙、材質與道路層一致；逐步調整非互動遠景、陰影範圍、特效、材質細節及內部解析度，檢查退化的可見代價與邊界閃爍。調節採平滑與滯後，不在單幀突然改變整個山體。無法同時達成目標時，記錄瓶頸、實際畫質與可維持幀率，不能聲稱已達最高畫質。

## 完成門檻

所見即所得、地形連續與資源生命週期是硬門檻；畫質候選必須先通過，再比較效能。發布前固定目標裝置與閾值，填入可重現的逐場景結果，保留尚未達標或未支援的項目。現有欄位的null代表未量測，不代表零成本或通過。
